Abstract
Serverless computing delivers elastic, event-driven execution of cloud functions without explicit infrastructure
management, yet suffers from a persistent performance bottleneck: the cold start—latency incurred when a
container must be provisioned, initialized, and loaded with dependencies before execution begins. Cold-start
mitigation is fundamentally a constrained optimization problem: prewarming containers reduces latency but
wastes resources on idle capacity, while aggressive reclamation conserves resources but increases user-facing
latency and SLA violations. Existing approaches address fragments of this problem—static keep-alive policies,
workload-prediction-based provisioning, isolated fuzzy or metaheuristic controllers, and dependency-aware
scheduling—but no framework jointly addresses reasoning under workload uncertainty, exploiting inter-
function dependency structure for sub-container-level resource sharing, and solving the resulting constrained
multi-function allocation problem under hard resource budgets.
This paper presents GranuWarm, a closed-loop adaptive prewarming framework that integrates three
complementary mechanisms, each with a distinct architectural role. A Mamdani-type fuzzy inference system
maps real-time workload signals—invocation intensity, traffic trend, cold-start pressure, and resource
utilization—to per-function warm-capacity recommendations, enabling uncertainty-aware reasoning without
requiring accurate long-horizon workload predictions. A dependency granularity tree decomposes the
function fleet's software stacks into hierarchical, shareable layers (runtimes, libraries, function-specific code),
transforming the decision space from coarse per-function container counts to fine-grained resource units that
exploit inter-function overlap. A constrained Particle Swarm Optimizer then searches for the globally
optimal allocation of warm resources across granularity-tree nodes, minimizing a composite objective of cold-
start latency, cold-start frequency, idle-resource cost, and SLA-violation rate, subject to platform memory and
capacity constraints. GranuWarm employs a dual-timescale architecture: the fuzzy controller runs on a fast
loop (5–10 s) for rapid adaptation, while the PSO optimizer runs on a slower loop (30–60 s) for periodic global
re-optimization. We evaluate GranuWarm on a Kubernetes/Knative testbed with 12 heterogeneous benchmark
functions under five workload regimes—stable, gradual-growth, bursty, periodic, and non-stationary—and
conduct a systematic six-configuration ablation study. Results demonstrate that GranuWarm achieves a
superior Pareto frontier on the latency–resource tradeoff, reducing P95 cold-start latency and SLA violations
compared to all baselines while maintaining comparable or lower resource consumption, and that each
architectural component contributes measurably to overall performance.

1. Introduction
1.1 The Serverless Computing Paradigm
Cloud computing has undergone a progressive shift from Infrastructure-as-a-Service (IaaS), where users
manage virtual machines, through Platform-as-a-Service (PaaS), where the runtime environment is managed,
to Function-as-a-Service (FaaS), where the unit of deployment is a single stateless function [1]. In the FaaS
model—commercially realized by AWS Lambda, Google Cloud Functions, Azure Functions, and open-source
platforms such as Knative [2], OpenFaaS [3], and Apache OpenWhisk [4]—developers deploy event-triggered
functions without provisioning or managing servers. The platform handles container lifecycle management,
automatic horizontal scaling, and crucially, scale-to-zero: when a function receives no invocations for a
configurable period, its containers are deallocated entirely, eliminating idle-resource costs.
This elasticity has driven rapid adoption. Datadog's 2024 State of Serverless report indicates that over 70% of
organizations using cloud services have adopted serverless technologies in some capacity [5]. However, the
scale-to-zero capability introduces a well-documented performance challenge that remains a primary obstacle
to serverless adoption for latency-sensitive applications: the cold start.
1.2 Anatomy of a Cold Start
When a function is invoked and a pre-initialized container is available (a warm start), the request is dispatched
directly, incurring only network and execution latency—typically single-digit milliseconds. When no warm
container exists (a cold start), the platform must execute a multi-stage initialization pipeline:

Empirical measurements across major cloud providers reveal that cold-start latencies range from

warm-start P99 by 10–50×.
For applications where end-to-end latency is critical—interactive web APIs, real-time data processing
pipelines, IoT event handlers, and microservice chains where cold starts compound multiplicatively—this
performance penalty can render serverless architectures unsuitable, forcing architects to either over-provision
resources (negating the cost benefits of serverless) or accept degraded user experience.

Cold-start mitigation is not simply a matter of "keeping containers alive longer." It is fundamentally a
constrained bi-objective optimization between two competing goals:
Objective 1 — Minimize cold-start impact:
Objective 2 — Minimize resource waste:
where

These objectives are in direct tension. Aggressive prewarming (maintaining many warm containers) minimizes
cold starts but increases idle-resource costs. Aggressive reclamation (quickly deallocating idle containers)
conserves resources but increases cold-start frequency and latency. The optimal operating point is workload-
dependent and shifts over time.
This tradeoff is compounded by four characteristics of real serverless workloads that defeat simple heuristics:
1. Burstiness. Invocation rates exhibit heavy-tailed distributions with sudden, unpredictable spikes. A
function averaging 5 req/s may experience bursts of 500 req/s during flash events [9].
2. Non-stationarity. Workload distributions shift continuously—diurnal cycles, weekly patterns, seasonal
effects, and regime changes mean that historical statistics become stale [10].
3. Heterogeneity. Functions differ vastly in cold-start cost (0.1 s to 10+ s), memory footprint (64 MB to 3+
GB), invocation frequency (sub-second to hours), and latency sensitivity [7].
4. Resource constraints. The platform has finite memory, CPU, and budget. Resources allocated to pre-
warming one function are unavailable for others.
The central research question is therefore not "Should we prewarm?" but:
Given the current and anticipated workload state, finite platform resources, and per-function SLA
requirements, what is the optimal allocation of warm capacity across the function fleet—at what
granularity—and how should this allocation adapt over time?
1.4 Limitations of Existing Approaches
The literature on serverless cold-start mitigation has advanced significantly through 2025–2026. We identify
five categories of existing work, each addressing a subset of the problem dimensions outlined above:
Category 1: Static and threshold-based policies. The simplest approach—and the default in most
production platforms—uses fixed keep-alive timers (e.g., AWS Lambda's ~10-minute idle timeout) or static
minimum-instance counts [11, 12]. These are non-adaptive: a fixed keep-alive wastes resources during low-
traffic periods and provides no protection against bursts exceeding pre-allocated capacity. Provisioned
concurrency features (e.g., AWS Provisioned Concurrency) allow users to specify static minimum warm
instances but require manual tuning and incur costs regardless of utilization.
Category 2: Prediction-based prewarming. Recent work applies time-series forecasting—ARIMA, LSTM
networks, spatio-temporal models, and transformers—to predict future invocation rates and proactively

treated as monolithic deployment units; instead, shared dependencies can be maintained at finer granularity.
This structural insight is valuable but does not incorporate an explicit adaptive control mechanism for
dynamically adjusting prewarming levels under changing workload and resource conditions—the scheduler
decides what to share but not how much to prewarm under uncertainty.
Category 4: Fuzzy-control-based approaches. Fuzzy logic has been applied to serverless resource
management in two notable instances: a 2025 Chinese patent application [17] describing fuzzy-controlled
container preheating with inputs including invocation count, execution time, and memory, and the 2026
WarmFlex system [18], which uses a fuzzy controller to adapt keep-alive duration based on inter-arrival time
feedback. These demonstrate that fuzzy inference naturally handles the imprecise, gradual nature of workload
characterization ("traffic is moderately high," "memory pressure is increasing"). However, both operate at the
individual-function level—each function's prewarming decision is made independently—and neither
addresses the constrained multi-function allocation problem where prewarming one function consumes
resources needed by another.
Category 5: Metaheuristic optimization. PSO, genetic algorithms, and ant colony optimization have been
applied to cloud resource scheduling and container placement [15, 19, 20]. These approaches can find good
solutions to combinatorial allocation problems but typically operate as standalone optimizers without
integrated uncertainty-aware reasoning or dependency-structure-aware search spaces. Without a meaningful
objective signal derived from workload state, they optimize blind.

1.5 Proposed Approach: GranuWarm
We propose GranuWarm (Granularity-aware Warm-capacity controller), a closed-loop adaptive prewarming
framework that assigns each technique a distinct, architecturally motivated role:
Fuzzy Inference System → Reasons under workload uncertainty to produce per-function warm-
capacity recommendations.
Dependency Granularity Tree → Transforms the per-function decision space into a finer-grained,
dependency-aware resource-unit space that exploits inter-function sharing.
Constrained PSO → Searches for the globally optimal allocation of warm resources across granularity-
tree nodes under hard resource constraints.
Feedback loop → Observed post-decision metrics (latencies, cold-start rates, resource utilization) feed
back to close the control loop.
Critically, GranuWarm employs a dual-timescale architecture: the computationally lightweight fuzzy
controller executes on a fast loop (every 5–10 s) for rapid reactive adaptation, while the heavier PSO optimizer
executes on a slower loop (every 30–60 s) for periodic global re-optimization. This separation prevents
optimizer overhead from becoming a bottleneck while maintaining fast responsiveness to workload shifts.
1.6 Contributions
The principal contributions of this work are:
1. A novel problem formulation that frames serverless prewarming as constrained optimization over a
dependency-granularity search space, moving beyond per-function container counts to shared-layer
resource allocation.
2. A unified closed-loop architecture integrating workload-uncertainty-aware fuzzy control,
dependency-structure-aware granularity decomposition, and constrained multi-objective PSO into a
single adaptive framework, with each component addressing a distinct problem dimension.
3. A dual-timescale control design separating fast, lightweight fuzzy adaptation from periodic global
PSO optimization, balancing responsiveness against computational overhead.
4. A comprehensive experimental evaluation with a systematic six-configuration ablation study across
five workload regimes, demonstrating that each architectural component contributes measurably and

1.7 Research Questions
This work is guided by three experimentally testable research questions:

2. Related Work
This section surveys the five streams of prior work most relevant to GranuWarm: serverless cold-start
characterization, prewarming and keep-alive strategies, dependency-aware scheduling, fuzzy control in cloud
systems, and metaheuristic optimization for resource management.
2.1 Cold-Start Characterization
Understanding the sources and magnitude of cold-start latency is foundational. Mohan et al. [6] provided one
of the earliest systematic measurements of cold-start latency across AWS Lambda, Google Cloud Functions,
and Azure Functions, finding that runtime choice (interpreted vs. compiled), deployment package size, and
allocated memory significantly impact initialization time. Wang et al. [7] extended this analysis with a deeper
investigation of AWS Lambda's container lifecycle, documenting the internal stages of cold-start initialization
and identifying that dependency loading—not container provisioning—dominates cold-start time for
functions with large packages.
Shahrad et al. [9] presented the most comprehensive analysis to date, analyzing production traces from Azure
Functions comprising millions of function invocations. Key findings include: (i) function popularity follows a
heavy-tailed Zipf distribution—a small fraction of functions account for the majority of invocations; (ii) inter-
arrival times vary by orders of magnitude across functions; (iii) cold starts disproportionately affect
infrequently invoked functions; and (iv) a fixed 10-minute keep-alive policy results in substantial resource
waste for popular functions while providing inadequate protection for bursty ones.
Bermbach et al. [8] and Maissen et al. [21] developed benchmarking frameworks (FaaSdom) for systematic
cross-provider cold-start measurement, enabling reproducible comparison. These studies collectively establish
that cold-start mitigation is not a one-size-fits-all problem—different functions exhibit different cold-start
profiles, invocation patterns, and sensitivity to latency.

The simplest mitigation is extending keep-alive duration. Akkus et al. [11] proposed SAND, which uses
application-level sandboxing to share runtimes across functions within an application, reducing per-function
cold-start cost. Oakes et al. [22] introduced SOCK, which optimizes container initialization through lean
containers and import caching.
Prediction-based prewarming has received increasing attention. Shahrad et al. [14] proposed a hybrid
histogram-based policy that adapts keep-alive durations based on observed inter-arrival time distributions.
Suresh and Gandhi [13] developed ServerMore, which uses invocation history to predict upcoming requests
and opportunistically pre-warm containers. Lin and Khazaei [23] applied LSTM-based time-series forecasting
to predict function invocation volumes and pre-provision containers accordingly.
The 2026 WPPSO framework [15] represents the current state of the art, combining: (i) LLM-based extraction
of function features (resource requirements, dependency characteristics), (ii) a spatio-temporal neural network
for workload prediction, (iii) greedy initialization for container placement, (iv) discrete PSO for container-
function matching, and (v) hierarchical container recycling. Evaluated on Knative, WPPSO reports 72.2% lower
startup latency and 63.4% lower memory footprint versus native Knative autoscaling. However, WPPSO's
reliance on accurate workload prediction makes it vulnerable to forecast errors during regime changes and
unprecedented bursts.
2.3 Dependency-Aware and Fine-Grained Scheduling
Rather than treating each function deployment as monolithic, several approaches exploit dependency
structure for optimization. Hanaforoosh et al. [16] proposed a granularity-tree-based scheduler where
functions' dependency stacks are represented as hierarchical trees, enabling the platform to maintain shared
dependency layers across functions. Their evaluation on Kubernetes + Fission demonstrated reduced cold-
start latency through dependency reuse. Critically, their scheduler makes deployment-time decisions about
dependency sharing but does not dynamically adjust prewarming levels at runtime.
Du et al. [24] explored checkpoint/restore mechanisms (CRIU) to snapshot initialized containers and rapidly
restore them, effectively amortizing cold-start cost across invocations. Cadden et al. [25] proposed unikernels
as lightweight alternatives to containers, eliminating OS-level overhead. These approaches are complementary
to—rather than competing with—GranuWarm's control-layer optimization.
2.4 Fuzzy Control in Cloud Resource Management
Fuzzy logic has a long history in control systems [26] and has been applied to cloud computing for VM
provisioning, load balancing, and autoscaling. Jamshidi et al. [27] demonstrated fuzzy autoscaling for multi-
tier web applications, showing that fuzzy controllers can adapt to workload changes without precise
mathematical models of the system being controlled.
In the serverless domain specifically, a 2025 Chinese patent application [17] describes a fuzzy-control-based
container preheating method with inputs including historical invocation count, average execution time, and
memory usage, producing a preheated-container count as output. The 2026 WarmFlex system [18] uses a
Mamdani fuzzy controller to adapt keep-alive duration based on inter-arrival time feedback, demonstrating
that fuzzy logic can effectively navigate the keep-alive tradeoff. Both systems, however, operate per-function
independently—they cannot reason about multi-function resource competition or exploit dependency
sharing.

PSO [28] and its variants have been extensively applied to cloud task scheduling, VM placement, and container
orchestration [19, 20]. Typical formulations encode resource allocations as particle positions and optimize
makespan, cost, or energy consumption. Discrete and constrained PSO variants handle integer decision
variables and resource budgets through penalty functions or repair operators.
In the serverless context, WPPSO [15] uses discrete PSO for container-function matching after workload
prediction. However, its PSO operates over a per-function container assignment space, not a dependency-
granularity-aware space, and is tightly coupled with the prediction model rather than an adaptive control
layer.
2.6 Positioning of GranuWarm
GranuWarm differs from all prior work in three respects:
1. Problem formulation. We formulate prewarming as constrained optimization over dependency-
granularity-tree nodes—a richer search space than per-function containers—under a multi-objective
fitness function incorporating latency, cold-start rate, resource cost, and SLA violations.
2. Architectural integration. Rather than using fuzzy control alone (WarmFlex), PSO alone (WPPSO), or
granularity analysis alone (Hanaforoosh), GranuWarm assigns each a distinct, non-redundant role: fuzzy
control for uncertainty-aware recommendation, granularity tree for search-space transformation, and
constrained PSO for global optimization.
3. Closed-loop adaptive control. GranuWarm continuously observes system state and adapts, unlike
static scheduling or one-shot optimization approaches.

        Dependency manifests D(fᵢ) for each function

3.      Extract dependency list D(fᵢ) = {(pkg, version), ...}

5.  end for
6.  
7.  // Layer 0: Shared runtimes
8.  for each unique runtime r do
9.      Create node v_r with memory m_r and init time τ_r
10.     V ← V ∪ {v_r}
11. end for
12. 
13. // Layer 1: Shared library bundles
14. Compute pairwise dependency overlap: O(fᵢ, fⱼ) = D(fᵢ) ∩ D(fⱼ)
15. Apply agglomerative clustering on dependency sets using Jaccard similarity
16. for each cluster of shared dependencies S do
17.     Create node v_S with memory Σ_{d∈S} m_d
18.     V ← V ∪ {v_S}

7. Limitations and Threats to Validity
7.1 Internal Validity
Workload representativeness. Our five workload regimes, while canonical, do not capture all real-world
serverless traffic patterns. Production workloads may exhibit more complex temporal correlations, multi-
modal distributions, or cascading patterns from microservice dependencies. We mitigate this by including the
non-stationary regime (W5) and bursty regime (W3), which stress-test adaptiveness.
Parameter sensitivity. GranuWarm's performance depends on several design parameters: fuzzy membership
function shapes, rule base, PSO hyperparameters, objective weights, and control loop intervals. While we
conduct sensitivity analyses (Section 6.6), exhaustive parameter search is infeasible. The chosen defaults are
guided by standard fuzzy/PSO design practices and preliminary tuning.
Cold-start estimation. The fitness function (Section 4.5.2) estimates cold-start impact based on current
allocation and workload state. These estimates are approximations; actual cold-start behavior depends on
factors not modeled (e.g., container image cache state, node-level resource contention).
7.2 External Validity
Platform specificity. Our evaluation uses Knative on Kubernetes. While GranuWarm's architecture is
platform-agnostic (any platform supporting programmatic scale control), specific behaviors (container startup
times, scheduling latency, autoscaler interactions) may differ on AWS Lambda, Azure Functions, or other
platforms.
Scale. Our testbed has 12 functions on a 4-node cluster. Production serverless platforms host thousands of
functions on much larger clusters. The PSO's search space grows linearly with the number of granularity-tree
nodes (
), and PSO's scalability to 
 would require investigation—potentially decomposition
strategies or alternative optimizers.
Function characteristics. Our benchmark functions are synthetic, designed to create dependency overlap.
Real function fleets may have more or less overlap, affecting the benefit of granularity-aware optimization.
7.3 Construct Validity
Composite objective. The weighted-sum objective  assumes linear combination of metrics. In practice,
stakeholders may have non-linear preferences (e.g., "latency doesn't matter until it exceeds the SLA, then it

Fuzziness coefficient selection. The membership functions and rule base encode domain knowledge that

but reduce interpretability.
8. Conclusion
8.1 Summary
This paper presented GranuWarm, a closed-loop adaptive prewarming framework for serverless cold-start
mitigation that addresses three dimensions underserved by prior work: workload uncertainty, inter-function
dependency structure, and constrained multi-function resource allocation.
GranuWarm introduces a novel problem formulation—constrained optimization over a dependency-
granularity search space—and an integrated architecture where a Mamdani fuzzy controller provides
uncertainty-aware warm-capacity recommendations, a dependency granularity tree transforms the per-
function decision space into fine-grained, shareable resource units, and a constrained PSO optimizer finds the
globally optimal allocation under hard resource budgets. A dual-timescale control design separates rapid
fuzzy adaptation (5–10 s) from periodic global PSO re-optimization (30–60 s), balancing responsiveness
against computational overhead.
Experimental evaluation on a Kubernetes/Knative testbed with 12 benchmark functions under five workload
regimes, including a systematic six-configuration ablation study, demonstrates that:
[RQ1] Fuzzy control significantly reduces cold-start frequency and latency compared to static policies,
particularly under bursty and non-stationary workloads.
[RQ2] Constrained PSO optimization improves the latency–resource Pareto tradeoff beyond what fuzzy
or PSO achieves independently.
[RQ3] Dependency-granularity awareness improves resource efficiency by enabling shared-layer
prewarming.
8.2 Future Work
Several directions merit investigation:
1. Adaptive membership functions. Replacing hand-crafted fuzzy membership functions with ANFIS
(Adaptive Neuro-Fuzzy Inference System) to learn from operational data.
2. Multi-objective PSO. Replacing the weighted-sum fitness with true multi-objective optimization (e.g.,
MOPSO) to discover the Pareto frontier directly.
3. Hierarchical control. For large function fleets (
), decomposing the optimization into per-
cluster or per-application subproblems with a global coordinator.
4. Integration with prediction. Combining GranuWarm's reactive fuzzy control with lightweight workload
prediction for proactive prewarming of anticipated bursts.
5. Multi-cloud deployment. Extending the framework to heterogeneous multi-cloud environments
where functions may be deployed across providers with different cold-start characteristics.
